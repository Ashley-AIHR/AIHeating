# P9 Implementation Plan

## Boundary

P9 validates and freezes the accepted synthetic PoC. It does not retrain P4, recalibrate P5, retune P6, regenerate canonical evidence, connect a live LLM, add equipment integration, or build a new live runtime.

## Sequence

1. Verify the registered P0–P7 integrity chain and bind the accepted P8 implementation/evidence boundary.
2. Prove the active runtime path from source and executable tests. Freeze Guided Evidence Mode unless a complete interval-by-interval P1A→P4→P5→P6 loop is present.
3. Pin release versions and hashes, then verify the release manifest before tests.
4. Run P9 runtime, status, security, deterministic replay, browser, responsive, accessibility and acceptance checks.
5. Run the complete inherited P0–P8 regression, exact frontend build and a clean temporary frontend install/build.
6. Verify P0–P8 integrity and the release manifest after tests; publish the release evidence and decision.

## Decision rule

Any frozen hash failure, canonical evidence change, build failure, unsafe application transition, misleading status, invented Tutor telemetry, or unsupported customer claim makes P9 fail. Accepted synthetic-only, deterministic-Tutor and deferred-live-runtime limitations remain explicit and non-blocking.
